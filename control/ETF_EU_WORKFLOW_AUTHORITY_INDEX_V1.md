# Weekly ETF EU Workflow Authority Index V1

Status: ACTIVE CANDIDATE STANDARD  
Product: `weekly_etf_eu`  
Authority scope: operational workflow topology only

## Purpose

This file defines which GitHub Actions routes may participate in the current Weekly ETF EU production lifecycle. It prevents historical activation, preview, repair, donor-runtime and delivery workflows from silently becoming parallel production authority.

## Canonical topology

### 1. Candidate build route

Canonical workflow:

`/.github/workflows/run-weekly-etf-eu-routine.yml`

Authority:
- build a candidate on a non-`main` branch;
- obtain current EU/UCITS pricing and macro evidence;
- construct NL/EN client artifacts;
- run machine validation;
- render review pages;
- persist generated candidate evidence to the same candidate branch;
- upload review evidence.

Explicitly not authorized:
- pushing generated candidate output directly to `main`;
- granting independent assurance;
- merging the candidate;
- creating delivery authority;
- sending email;
- mutating protected portfolio/trade-ledger authority;
- real broker execution.

A v2 routine request must declare:

```text
execution_mode=generate_validate_candidate
delivery_authority=false
```

The candidate pricing authority is the EU/UCITS v2 path used by this workflow. Retained donor module `pricing.run_pricing_pass` is not an ETF EU release/runtime authority.

### 2. Independent assurance route

Independent assurance is not generated by the candidate workflow.

A `governance_release_assurance` reviewer must review one exact frozen candidate head and produce an explicit:

`PASS | FAIL | INDETERMINATE`

The reviewer must be separate from `implementation_operations`. Any semantic candidate change after review invalidates the verdict and requires fresh assurance.

Machine checks, generated release evidence or validation JSON are supporting evidence only. They are never a substitute for independent role-B assurance.

### 3. Merge / exact-main route

A candidate may be merged only after independent `PASS` on the exact frozen head and after confirming the reviewed head has not changed.

After merge, exact-main validation must confirm that the approved candidate is present on `main`, that no unreviewed semantic change entered the product boundary and that no active donor/legacy workflow writes non-EU product state back to `main`.

### 4. Guarded delivery route

Canonical workflow:

`/.github/workflows/send-weekly-etf-eu-controlled-transport.yml`

This is the only active workflow allowed to invoke the real ETF EU controlled sender.

It is `main`-only and requires a committed `etf_eu_guarded_delivery_authority_v1` JSON record containing:
- product identity `weekly_etf_eu`;
- report run/date/suffix;
- exact independently assured candidate head SHA;
- exact approved report commit SHA on `main`;
- independent assurance verdict `PASS` plus evidence reference;
- evidence that implementation and assurance roles were separate;
- explicit principal guarded-send authorization and reference;
- the six approved NL/EN Markdown/HTML/PDF artifact paths;
- SHA-256 for every approved artifact;
- `portfolio_mutation=false`;
- `broker_execution=false`.

The transport workflow:
- validates every hash before transport;
- confirms the approved report commit is in current `main` lineage;
- does not re-render the report;
- sends the exact approved artifacts;
- records transport evidence separately;
- may not claim inbox delivery without positive receipt evidence.

## Historical workflows

Twenty-three historical activation/send/repair/preview/client-like/donor-runtime routes are retained only as files ending in `.yml.disabled`. GitHub Actions must not treat them as executable workflows.

The disabled set includes prior:
- Stage-1/CAP01 activation;
- dated fresh-send;
- routine preview/recovery;
- shadow CID delivery;
- corrected/current-package/general send routes;
- split-test send routes;
- client-surface/PDF repair routes;
- report-to-state refresh authority inversion;
- old client-grade render/preview/export routes;
- the 2026-07-27 allocator `sister report` shadow route that rendered a client-like report from the historical transition allocator;
- `persist-etf-pricing-audit.yml`, retired after it wrote US Weekly ETF holdings/pricing artifacts to ETF EU `main` during PR #91 post-merge validation;
- `validate-etf-runtime.yml`, retired because it executed the same US donor pricing path and legacy `send_report.py` renderer;
- `validate-etf-lane-breadth.yml`, retired after the hardened product-boundary scan showed it still validated donor `weekly_analysis_pro_*` report files. Its desired breadth behavior is now represented through the current donor-discovery → UCITS mapping/fundability bridge instead of an active US-report validator.

Historical code is audit evidence, not current authority. In particular, historical allocator diagnostics and donor US pricing/report modules may not create a second pricing, state or client-output surface beside the canonical EU candidate path.

## Post-merge donor-leak incident

PR #91 was independently PASSed and merged as `202b0a629af34c697c7b7cb8fdce97fbb56bddbc`. A still-active legacy pricing-audit workflow then committed `d771bde734ffda6120a77b1f4fe0e99bd198cc96`, adding US holdings/pricing artifacts (GLD/GSG/PAVE/PPA/SMH/SPY/URNM) rather than the protected EU funded set (VWCE/EUNA/SXR8/L0CK).

The strengthened gate then found a third active donor-report validator, `validate-etf-lane-breadth.yml`. It did not mutate portfolio state, but it was still anchored to the wrong product output namespace (`weekly_analysis_pro_*`) and therefore belonged in historical donor audit evidence rather than the active ETF EU topology.

The incident establishes this additional authority rule:

> Green CI does not create product identity. An active ETF EU workflow may not invoke retained US Weekly ETF donor execution surfaces.

Prohibited active-workflow execution tokens include at minimum:
- `pricing.run_pricing_pass`;
- `output/etf_portfolio_state.json`;
- `weekly_analysis_pro_`;
- `send_report.py` / `import send_report`;
- `etf.txt`;
- `etf-pro.txt`.

These tokens may exist in `.yml.disabled` historical audit files, but not executable `.yml/.yaml` workflows.

## Research and validation workflows

Diagnostic, pricing, lab, probe and validation workflows may remain active when they are genuinely EU-scoped and non-authoritative. They must not:
- create funding authority;
- mutate the protected portfolio or trade ledger;
- invoke real delivery;
- create independent assurance;
- turn report text into portfolio state;
- render a parallel client-like report from a historical/shadow allocator;
- execute the donor US pricing/report runtime or validate donor report filenames as if they were ETF EU outputs.

## Enforced gate

`tools/validate_etf_eu_workflow_authority.py` must pass on every donor-parity/release-repair PR. `tools/validate_etf_eu_repository_boundary.py` provides a second independent product-boundary scan.

The gates verify at minimum:
- retired workflow names are not active `.yml/.yaml` files and their `.disabled` audit copies exist;
- no active workflow contains US donor execution tokens;
- candidate workflow cannot send, self-assure or push candidate output to `main`;
- controlled transport requires exact guarded-delivery authority;
- controlled transport does not re-render approved client artifacts;
- there is exactly one active real ETF EU delivery invocation;
- the historical allocator sister-report and donor runtime/report-validator routes remain retired.

## Authority hierarchy

For operational routing:

`this index + current runbook > active canonical workflows > supporting EU validation workflows > .disabled historical workflows`

For allocation/funding authority, defer to `control/ETF_EU_ALLOCATION_AUTHORITY_V1.md` and the protected portfolio/trade-ledger state. This file does not create allocation authority.
